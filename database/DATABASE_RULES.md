# AUSTRC Database Rules — Neon PostgreSQL

**Database Implementation Version:** `1.1.0`  
**Platform:** Neon PostgreSQL

These rules apply to all developers, reviewers, scripts, and AI coding assistants.

---

# 1. Mandatory rules

1. Never create a table before searching the approved 56-table schema.
2. Never modify another module's tables directly.
3. Never add an Event → Administration or Administration → Event foreign key.
4. Never make Shared/Core depend on module tables.
5. Never duplicate users, members, roles, permissions, files, emails, generated documents, registrations, forms, certificates, or task concepts.
6. Every permanent schema change must be represented by a PostgreSQL migration in Git.
7. Never edit a migration that has already been merged/applied.
8. Never mix MySQL syntax into the PostgreSQL schema.
9. Breaking changes require an expand/migrate/contract plan.
10. Update schema documentation and changelog with every approved structural change.

---

# 2. PostgreSQL-only rule

This project uses Neon PostgreSQL.

Do not generate:

```sql
AUTO_INCREMENT
LONGTEXT
ON UPDATE CURRENT_TIMESTAMP
UNIQUE KEY ...
KEY idx_name (...)
```

Use PostgreSQL equivalents:

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY
TEXT
TIMESTAMPTZ
JSONB
CONSTRAINT name UNIQUE (...)
CREATE INDEX name ON table_name (...)
```

Automatic `updated_at` behavior must use the approved PostgreSQL trigger pattern or an explicitly approved application-managed alternative.

# 4. AI protocol

Before database-related code, an AI must:

1. Read all database Markdown files.
2. Inspect `current_schema.sql`.
3. Search for an existing table serving the requested concept.
4. Identify the table owner.
5. Reuse existing relationships.
6. Avoid new tables when the requirement fits an existing dynamic/configuration/history structure.
7. If a new table/breaking change appears necessary, stop and produce a schema-change proposal.

Required proposal:

```text
SCHEMA CHANGE PROPOSAL

Feature:
Existing tables reviewed:
Why existing schema is insufficient:
Owning module:
Proposed PostgreSQL change:
New/changed indexes:
New/changed constraints:
Backward compatibility:
Data migration/backfill:
Affected modules:
Deployment order:
```

# 5. Identity rules

`core_users` = software account/system identity.  
`core_members` = official AUSTRC club member.  
`evt_participants` = Event participant identity.

Do not create `admin_users`, `event_users`, `members_new`, or similar duplicates.

---

# 6. PostgreSQL identity columns

Primary-key baseline:

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Do not create manual `MAX(id)+1` logic.

When importing explicit historical IDs, ensure identity sequences are synchronized afterward if required by the migration/import procedure.

---

# 7. PostgreSQL timestamp rules

Use `TIMESTAMPTZ` for application/business timestamps.

Examples:

```text
created_at
updated_at
registered_at
submitted_at
issued_at
delivered_at
```

Store real instants in PostgreSQL and format them for the user's timezone at the application/UI layer.

Do not use MySQL `ON UPDATE CURRENT_TIMESTAMP`.

The baseline schema uses:

```text
set_updated_at()
```

and table triggers for rows containing `updated_at`.

---

# 8. JSONB rules

Use `JSONB` for flexible configuration/metadata.

Appropriate uses include:

- Validation rules
- Event configuration
- Result configuration
- Template variables
- Metadata
- Audit old/new values

Do not hide relational entities in JSONB when they require foreign keys, uniqueness, joins, reporting, independent lifecycle, or history.

If JSONB fields become heavily queried, add a reviewed PostgreSQL expression or GIN index only when actual query patterns justify it.

---

# 9. Unique-constraint and NULL rules

PostgreSQL UNIQUE constraints treat NULL values as distinct by default.

Therefore, multiple rows may satisfy a UNIQUE constraint when at least one constrained nullable column is NULL.

Use:

```sql
UNIQUE NULLS NOT DISTINCT (...)
```

only when the business rule requires NULL to behave like an equal value.

Do not change NULL uniqueness semantics casually; review existing data and application behavior first.

---

# 10. Email normalization

PostgreSQL normal string uniqueness is case-sensitive.

Application code must normalize login/account emails consistently, preferably:

```text
trim
lowercase
validate
store
```

Do not allow different application paths to store mixed-case duplicates.

If the project later wants database-enforced case-insensitive email uniqueness, add a reviewed expression index such as `LOWER(email)` or another approved PostgreSQL approach.

---

# 11. Foreign keys and deletes

Use FK constraints for real stable relationships.

General rules:

- `RESTRICT` for important business/history rows.
- `SET NULL` when the historical child can survive without the current optional account/template/file link.
- `CASCADE` only for true dependent/junction rows.

Never add a Shared/Core FK into `evt_*` or `adm_*`.

---

# 12. Historical snapshot rules

Snapshot columns are intentional historical evidence, not accidental duplication.

Examples:

- Participant name/email/phone snapshots
- Dynamic field key/label/type snapshots
- Certificate recipient/event/segment/position snapshots
- Application applicant snapshots
- Executive certificate term/position/team snapshots

Do not replace historical snapshot data with only a live join to mutable current records.

# 17. Result rules

Use:

```text

```

Do not duplicate segment/participant relationships inside result records when the registration-segment already provides the relationship.

Published/final results must not be silently overwritten; use revision history.

# 18. Panel-history rules

Historical member position/team identity belongs in:

```text

```

---

# 19. Task workflow rules

Use:

```text
adm_tasks
 -> adm_task_assignees
 -> adm_task_submissions
 -> adm_task_submission_files
 -> adm_task_submission_reviews
```

History/collaboration:

```text
adm_task_status_history
adm_task_comments
```

A revision creates a new submission version; it does not overwrite the previous submission.

---

# 20. PostgreSQL index rules

`PRIMARY KEY` and `UNIQUE` constraints already create supporting unique indexes.

Do not create duplicate indexes over the exact same key set without a query-performance reason.

Additional indexes must be based on actual filtering/join/sort usage.

Name indexes consistently:

```text
idx_<concept>_<columns>
```

---

# 21. Migration policy

Directories:

```text
database/migrations/shared/
database/migrations/event/
database/migrations/administration/
```

Recommended globally unique migration name:

```text
YYYYMMDDHHMMSS_<module>_<description>.sql
```

Examples:

```text
20260901103000_evt_add_team_size_to_events.sql
20260901114500_adm_add_task_category.sql
20260901130000_shared_add_user_locale.sql
```

Rules:

1. PostgreSQL syntax only.
2. Never modify applied migrations.
3. One clear purpose per migration.
4. Review by the owning module.
5. Shared changes require cross-team impact review.
6. Test against an empty/baseline database.
7. Test against representative existing data where possible.
8. Use transactions where appropriate and supported by the migration operation/tool.
9. Update `DATABASE_SCHEMA.md`.
10. Update `CHANGELOG.md`.
11. Update ERD if relationships change.

---

# 22. Expand-and-contract

For a breaking rename/removal:

1. **Expand** — add new structure while old remains.
2. **Migrate/backfill** — update data and code.
3. **Verify** — confirm old consumers are gone.
4. **Contract** — remove old structure in a later migration.

Do not drop a column required by another active branch/application version in the same migration that introduces its replacement.

---

# 23. Neon operational rule

Do not use Neon SQL Editor, `psql`, pgAdmin, or another console to make undocumented permanent production schema changes as normal development.

Emergency changes must be reconciled into a migration and Git immediately.

Keep credentials in environment variables and secret-management systems; never in source code or Markdown.
